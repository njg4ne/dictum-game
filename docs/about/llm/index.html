Working with an LLM

Dr. Nicholas Gardella built this site by directing Claude, a large language model (LLM) that writes and checks code. Claude did much of the typing and the testing. Dr. Gardella set the goals and judged the results. The game's engine, the part that makes the Latin word lists, is the students' work: read about it here.

Numbers on this page

  • Measured: we ran it, and a command in the project repeats it.
  • Cited: someone else published it. We say who they are and how far to trust them.
  • Estimate: our own arithmetic, with the assumptions shown.

LLMs do not speed everyone up. A 2025 study(opens in a new tab) by METR, a non-profit that tests AI systems, found that 16 experienced programmers working on large projects they knew well took 19% longer with an LLM. They believed it had saved them time. It is a preprint, so other scientists had not reviewed it yet, and it is small and covers one kind of work. It shows that LLMs do not always help. It does not show they never do. The tasks below are different: new code, unfamiliar tools, and checks a computer can run.

Accessibility checking #

The W3C, the group that sets the web's standards, says web accessibility means websites, tools and technologies are “designed and developed so that people with disabilities can use them” (W3C, Introduction to Web Accessibility(opens in a new tab)). It adds that accessibility “also benefits people without disabilities”: someone on a phone in bright sunlight, someone with a broken arm, older people, or anyone on a slow connection. This is the idea of universal design, which the United Nations defines as “the design of products, environments, programmes and services to be usable by all people, to the greatest extent possible” (Convention on the Rights of Persons with Disabilities, Article 2(opens in a new tab)). So the work below is for everyone who uses this site.

How hard is it? #

WebAIM(opens in a new tab), a non-profit at Utah State University, runs software over the home pages of the top million websites every year. In 2025, 94.8% had failures of the standard accessibility guidelines (WCAG), about 51 per page. The survey is large and long-running. It only counts what software can detect, and WebAIM says the true share of pages that fully pass is lower.

Checking by hand is slow. Tetralogical(opens in a new tab), an accessibility consultancy, estimates about 5 minutes for each of the 50 rules at levels A and AA, including the write-up. That is a working consultant's rule of thumb, not a measured average.

Estimate: 50 rules at 5 minutes is about 4 hours per page. This site has 8 pages and page states (the game, a guess in progress, two pop-ups, the instructor page, the students' page with and without test results, and this page). That is about 33 hours for one theme, before any fixes or re-checks. A newcomer would need longer.

How did the LLM check it? #

It wrote scripts/a11y.mjs. The script opens the built site in a real browser and runs axe-core(opens in a new tab), a free checker, against the WCAG 2.0, 2.1 and 2.2 rules at levels A and AA, in both the light and dark themes. It also ran Google's Lighthouse audit.

What came back? #

  • Measured: npm run a11y checks 16 page states and finds 0 problems. It takes about 10 seconds, so it ran after every change.
  • Measured: Lighthouse scored 100 for accessibility, best practices, SEO and speed on the game, instructor and About pages.
  • Control test: to confirm a clean result means something, the LLM added an image with no description, an unnamed button and faint text. The checker caught all three. They were then removed.
  • Also caught: a scrolling code box that keyboard users could not reach, and a sign-in check that could never be true.

What does that mean? #

There are no automated failures against WCAG 2.2 levels A and AA on the checked pages. That is not a certificate. Deque, the company that makes axe, reports in its own study(opens in a new tab) that automated tests find about 57% of issues. The study is from the vendor and we have not seen it repeated independently. Older rules of thumb say 20 to 30%. Either way, a person has to check the rest.

Where a person mattered: axe does not judge icons, so it passed icons whose two blues were too close to read. Dr. Gardella noticed. We then added a check that measures every icon in place, in both themes, against a 3:1 contrast rule. No one has yet tried the site with a real screen reader.

Python in the browser #

Python normally runs on a server. The brief asked for no server, so Python runs inside your web browser instead. The first step was to find out which parts of Python the Latin library needs. That can only be learned by trying.

  • The LLM tried MicroPython, a small version of Python, and showed it fails: it lacks several built-in parts the Latin library imports.
  • It switched to Pyodide(opens in a new tab), full Python rebuilt to run in a browser. The site serves its own copy, with no outside host.
  • Pyodide is about 14 MB, so only the pages that need it load it. A progress bar shows the download, and your browser keeps the files afterwards.
  • The students' code runs unchanged.

Checked by: 23 tests pass both in ordinary Python and inside the browser (you can run them), and a full test builds a real word list.

Comparing five student solutions #

Five working programs cannot be compared by reading them. The fair way is to run all five, unchanged, on the same input and measure. The aim was to learn what each approach does well, so the engine could take the best of each.

  • Measured: three teams shipped the vocabulary with their code, which means no network requests and a program that works offline. The engine does the same.
  • Measured: two teams chose the matching words before the slow lookup, which was about twice as fast as looking up everything first. The engine does the same.
  • Three teams told the library each word's part of speech, so the list holds only forms of words that are on the vocabulary list. The engine does the same, and also keeps only lowercase a to z, because the game cannot type capitals.
  • Comments in the engine credit each team at the line where its idea is used. A script copies their code word for word without running it. npm run check-credits fails if a team loses its credit.

The full report is src/lib/engine/PROFILING.md. The result is the students' engine.

Every valid Latin guess #

The question was whether the game could accept any real Latin form without shipping a huge word list. The LLM read the library's code, found it cannot look up a spelling, and measured instead of guessing.

  • Measured: the library produces about 1.4 million forms, but only 11,404 different five-letter spellings using a to z.
  • Measured: one per line, that is 68 KB. Storing each word as what it shares with the one before makes it 29 KB, or 7.8 KB compressed.
  • The LLM then updated every message, help text, test and document so each case is handled and described: too short, not Latin, real Latin that is not on the list, wrong, right.

Signing in with GitHub #

Signing in lets an instructor save word lists to their own GitHub account. This normally needs a server to keep a secret key. Here a small separate service keeps it, and this site only ever sees a short-lived code. The steps are fiddly, and a mistake is a security problem.

  • The LLM wrote the sign-in and the code that saves, lists, renames and deletes word lists. It asks GitHub for the smallest permission that can create a public repository.
  • Checked by a pretend GitHub in the tests, with no real account: it creates the repository, saves a list, lists it, renames it, deletes it and makes the student link.
  • It wrote GITHUB-OAUTH.md, listing the steps only a person can do.

Icons and dark mode #

  • The LLM chose 29 icons from 2,658 in a library, and wrote a script that recolors them to follow the light and dark themes.
  • It found its own bug by looking at screenshots: one icon had lost its outline.
  • Licenses were part of the work: each credit is on the attributions page.
  • A person caught what the LLM and the checker missed: icon colors too close together. That led to the in-place contrast check described above.

What the person did #

  • Wrote the brief: no server, no outside hosts, hints hidden by default, students credited by team. AUDIT.md records each decision and why.
  • Changed direction again and again. The original game accepted any Latin word, so the guess rules changed. The tests moved out of the instructor view. The About page split in two so the students' work is not buried.
  • Decided what to trust, and had the LLM say what it had not checked.

What was not checked #

  • The real GitHub sign-in, and how long GitHub takes to show a newly saved list.
  • Real screen readers, Safari and Firefox. Only Chrome's engine was tested.
  • Whether the valid-guess list matches what the original game accepted. It comes from Whitaker's Words, which has gaps.
  • Hours saved. Only the accessibility figures come from a source. We did not time a person doing the other tasks.

The full record is AUDIT.md in the repository. How it was made lists the tools.
